# Этап 1. Поразрядная сортировка (30 мин)

## Теория (кратко)

Пусть ключи — целые числа. Число $x$ в системе с основанием $k$ состоит из разрядов $d_0, d_1, \ldots$ (от младшего к старшему). Алгоритм:

1. Отсортировать массив устойчиво по разряду $d_0$.
2. Затем устойчиво по $d_1$, и так далее до старшего разряда.

**Почему это работает?** Индукция по номеру разряда: если перед шагом массив отсортирован по младшим разрядам, то после устойчивой сортировки по следующему разряду массив отсортирован по всем разрядам до текущего включительно. Равные разряды не «перетасовываются» именно из-за устойчивости — поэтому она критична.

Время: $d$ проходов по $\Theta(n + k)$, итого $\Theta(d(n + k))$.

## Шаг 1.1 — извлечение разряда

Начинаем с десятичных разрядов, чтобы алгоритм был наглядным:

```cpp
int getDigitDec(uint64_t key, int digitIndex) {
    for (int i = 0; i < digitIndex; i++) key /= 10;
    return key % 10;
}
```

## Шаг 1.2 — сортировка подсчётом по разряду: вся сортировка в одной функции

Напоминаем структуру из прошлой лабы (сортировка подсчётом), но теперь «значение» элемента — его текущий разряд, а проходов несколько. Вся поразрядная сортировка помещается в **одну функцию**:

```cpp
void radixSortDec(vector<uint64_t>& a) {
    if (a.empty()) return;
    int n = a.size();

    // сколько десятичных разрядов у самого большого числа
    uint64_t mx = *max_element(a.begin(), a.end());
    int maxDigits = 1;
    while (mx >= 10) { mx /= 10; maxDigits++; }

    for (int d = 0; d < maxDigits; d++) {
        // устойчивая сортировка подсчётом по d-му разряду
        vector<int> cnt(10, 0);
        for (int i = 0; i < n; i++) cnt[getDigitDec(a[i], d)]++;

        for (int i = 1; i < 10; i++) cnt[i] += cnt[i - 1]; // префикс-суммы

        vector<uint64_t> res(n);
        for (int i = n - 1; i >= 0; i--) // идём С КОНЦА => устойчивость
            res[--cnt[getDigitDec(a[i], d)]] = a[i];
        a = res;
    }
}
```

Обязательно обсудить два момента:
- **Почему обратный проход даёт устойчивость.** Префикс-сумма `cnt[d]` — позиция *последнего* элемента с разрядом `d`; идя с конца, мы расставляем равные элементы в исходном порядке.
- **Почему это работает.** Индукция по номеру разряда: если перед шагом массив отсортирован по младшим разрядам, то после устойчивой сортировки по следующему разряду он отсортирован по всем разрядам до текущего включительно.

**Точка контроля:** сортируем массив `{170, 45, 75, 90, 802, 24, 2, 66, 802}` (есть дубликат 802!) и сверяем с `std::sort` через `is_sorted` / сравнение копий.

## Шаг 1.3 — от десятичной версии к битовой за четыре замены

Десятичных проходов слишком много (до 20 для uint64). Хорошая новость: битовая версия **не пишется с нуля** — это та же функция, в которой сделаны четыре локальные замены:

| № | Было (десятичная) | Стало (битовая) | Зачем |
|---|---|---|---|
| 1 | `getDigitDec` — деление и остаток | `getDigitBits` — сдвиг и маска | извлекаем разряд из битов |
| 2 | `cnt(10, 0)` | `cnt(RADIX, 0)`, `RADIX = 256` | у разряда теперь 256 значений |
| 3 | `cnt[i] += cnt[i-1]` до `10` | тот же цикл до `RADIX` | префикс-суммы по новому размеру |
| 4 | `maxDigits` — зависит от данных | `digits = sizeof(uint64_t)` — константа 8 | 64 бита / 8 бит на разряд |

Константы и извлечение разряда сдвигом:

```cpp
const int BITS  = 8;
const int RADIX = 1 << BITS;   // 256
const int MASK  = RADIX - 1;   // 0xFF

int getDigitBits(uint64_t key, int digitIndex) {
    return (key >> (digitIndex * BITS)) & MASK;
}
```

Заметьте: `(key >> (d * 8)) & 255` математически то же самое, что `(key / 256^d) % 256` — мы просто считаем разряд в системе счисления с основанием 256. Сдвиг и маска быстрее деления, поэтому для степени двойки используем первый вариант.

Получившаяся функция:

```cpp
void radixSortBits(vector<uint64_t>& a) {
    if (a.empty()) return;
    int n = a.size();
    const int digits = sizeof(uint64_t); // 8 проходов для 64 бит

    for (int d = 0; d < digits; d++) {
        vector<int> cnt(RADIX, 0);
        for (int i = 0; i < n; i++) cnt[getDigitBits(a[i], d)]++;

        for (int i = 1; i < RADIX; i++) cnt[i] += cnt[i - 1];

        vector<uint64_t> res(n);
        for (int i = n - 1; i >= 0; i--) // с конца => устойчивость
            res[--cnt[getDigitBits(a[i], d)]] = a[i];
        a = res;
    }
}
```

Хорошее упражнение для студентов: применить четыре замены **самостоятельно** к своей `radixSortDec` и убедиться, что тесты по-прежнему зелёные — то, что обе версии совпадают с `std::sort`, подтверждает и замену.

Обсудить trade-off выбора `BITS`: `BITS = 1` → 64 прохода, крошечный `cnt`; `BITS = 16` → 4 прохода, `cnt` на 65 536 элементов. Оптимум обычно 8–16 бит.

## Код этапа целиком

```cpp
#include <iostream>
#include <vector>
#include <algorithm>
#include <cstdint>

using namespace std;

// ---------- Вариант 1: десятичные разряды ----------
// digitIndex = 0 -> единицы, 1 -> десятки, ...
int getDigitDec(uint64_t key, int digitIndex) {
    for (int i = 0; i < digitIndex; i++) key /= 10;
    return key % 10;
}

void radixSortDec(vector<uint64_t>& a) {
    if (a.empty()) return;
    int n = a.size();

    uint64_t mx = *max_element(a.begin(), a.end());
    int maxDigits = 1;
    while (mx >= 10) { mx /= 10; maxDigits++; }

    for (int d = 0; d < maxDigits; d++) {
        vector<int> cnt(10, 0);
        for (int i = 0; i < n; i++) cnt[getDigitDec(a[i], d)]++;

        for (int i = 1; i < 10; i++) cnt[i] += cnt[i - 1];

        vector<uint64_t> res(n);
        for (int i = n - 1; i >= 0; i--) // с конца => устойчивость
            res[--cnt[getDigitDec(a[i], d)]] = a[i];
        a = res;
    }
}

// ---------- Вариант 2: битовые разряды (по 8 бит) ----------
const int BITS  = 8;
const int RADIX = 1 << BITS;   // 256
const int MASK  = RADIX - 1;   // 0xFF

int getDigitBits(uint64_t key, int digitIndex) {
    return (key >> (digitIndex * BITS)) & MASK;
}

void radixSortBits(vector<uint64_t>& a) {
    if (a.empty()) return;
    int n = a.size();
    const int digits = sizeof(uint64_t); // 8 проходов для 64 бит

    for (int d = 0; d < digits; d++) {
        vector<int> cnt(RADIX, 0);
        for (int i = 0; i < n; i++) cnt[getDigitBits(a[i], d)]++;

        for (int i = 1; i < RADIX; i++) cnt[i] += cnt[i - 1];

        vector<uint64_t> res(n);
        for (int i = n - 1; i >= 0; i--) // с конца => устойчивость
            res[--cnt[getDigitBits(a[i], d)]] = a[i];
        a = res;
    }
}

int main() {
    vector<uint64_t> v = {170, 45, 75, 90, 802, 24, 2, 66, 802};
    radixSortBits(v);
    for (auto x : v) cout << x << " ";
    cout << endl;
    return 0;
}
```

## Типичные ошибки
- Проход по входу **вперёд** при сборке через префикс-суммы — сортировка перестаёт быть устойчивой, поразрядная сортировка ломается на дубликатах.
- Размер `cnt` не согласован с извлечением разряда: оставили `cnt(10, 0)`, а разряд берётся битовый — значения 10..255 уедут за границы массива (UB).
- `int digit` вместо `uint64_t key` — старшие разряды теряются.
- Забыли `cnt[i] += cnt[i-1]` и использовали счётчики как позиции.
- Сравнение с `std::sort` без дубликатов в тестовых данных (устойчивость тогда не проверяется).

# Этап 2. Бенчмарки (30 мин)

## Теория: как измерять корректно

1. Компилируем **с `-O2`** — без оптимизации замеры бессмысленны.
2. Меряем на **копии** данных: сортировка мутирует массив, второй прогон получит уже отсортированные данные.
3. Делаем несколько прогонов и берём **медиану** (устойчива к выбросам от ОС/диска).
4. Данные не должны «выбрасываться» оптимизатором (dead code elimination) — используем результат (например, `is_sorted`).
5. Время меряем `std::chrono::steady_clock` (монотонные часы; `system_clock` может «прыгать»).

## Шаг 2.1 — свой генератор случайных чисел: xorshift64

Самим сортировкам генератор не нужен — он нужен только для **генерации тестовых данных и стресс-тестов**, поэтому живёт в этом этапе. И здесь «простой» `rand()` не подходит по трём причинам:

1. **Диапазон.** `rand()` возвращает `int` из $[0, \text{RAND\_MAX}]$, а `RAND_MAX` стандарт не фиксирует: на Windows (MSVC) это всего 32767, на Mac/Linux — $2^{31}-1$. Ключи у нас 64-битные — `rand()` физически не может заполнить старшие биты, и проходы старших разрядов всегда будут сортировать нули. Тест станет «зелёным», но не будет проверять половину алгоритма.
2. **Воспроизводимость.** Стандарт не задаёт последовательность `rand()` — на другой машине или компиляторе упавший тест не повторится.
3. **Качество.** У `rand()` слабые младшие биты — а поразрядная сортировка работает именно с ними.

Вместо этого пишем собственный генератор — классический **xorshift64** (Дж. Марсалья, 2003). Пять строк, внутри только сдвиги и XOR — операции, которые студенты только что применили в самой сортировке:

```cpp
uint64_t rngState = 42; // фиксированный seed: упавший тест можно повторить

uint64_t rnd() {
    rngState ^= rngState << 13;
    rngState ^= rngState >> 7;
    rngState ^= rngState << 17;
    return rngState;
}
```

Чем это хорошо:
- **Полный 64-битный диапазон** — каждый вызов даёт значение со всеми 64 «случайными» битами, все 8 проходов сортировки реально тестируются.
- **Воспроизводимость**: seed задан константой, последовательность одинакова на любой машине — упавший стресс-тест повторяется точно.
- **Прозрачность**: никаких магических типов из `<random>`; за пару минут можно обсудить, почему сдвиги и XOR «перемешивают» биты.

Типичный вопрос на этом месте: *«rnd() же всегда вернёт одно и то же?»* Ответ состоит из двух половин:
- **Внутри одного запуска — нет.** Каждый вызов изменяет `rngState`, поэтому последовательность вызовов даёт разные числа (проверьте: три вызова подряд — три разных значения). Период xorshift64 — $2^{64}-1 \approx 1.8 \cdot 10^{19}$: до зацикливания последовательность не дойдёт.
- **Между запусками программы — да.** Seed фиксирован, поэтому каждый запуск получает ту же самую последовательность. Это не баг, а режим воспроизводимости: упавший тест повторяется точно, а все сортировки в бенчмарке получают идентичные входные данные — сравнение честное.

Если для отдельного эксперимента нужны разные данные от запуска к запуску, seed берут из времени: `rngState = time(nullptr);`. Для лабы фиксированный seed удобнее.

Честная ремарка для любопытных: xorshift не проходит строгие статистические тесты и не годится для криптографии — но для генерации тестовых данных его качество более чем достаточно. Ремарка о точности: `rnd() % K` даёт лёгкий перекос распределения (модуль состояния не всегда кратен $K$); для лабы это допустимо, строгий вариант — `uniform_int_distribution` из `<random>`.

## Шаг 2.2 — генераторы данных

Разные распределения дают разные выводы. Случайные значения берём из `rnd()` (xorshift64 из шага 2.1 — полный 64-битный диапазон и воспроизводимость при фиксированном seed):

```cpp
vector<uint64_t> randomData(int n) {
    vector<uint64_t> v(n);
    for (auto& x : v) x = rnd();
    return v;
}

vector<uint64_t> sortedData(int n) {
    vector<uint64_t> v(n);
    for (int i = 0; i < n; i++) v[i] = i;
    return v;
}

vector<uint64_t> reversedData(int n) {
    vector<uint64_t> v(n);
    for (int i = 0; i < n; i++) v[i] = n - i;
    return v;
}

vector<uint64_t> fewUniqueData(int n) {
    vector<uint64_t> v(n);
    for (auto& x : v) x = rnd() % 10; // всего 10 разных значений
    return v;
}
```

Обсудить со студентами, зачем нужны все четыре:
- `randomData` — базовый случай, средний по «трудности»;
- `sortedData` — лучший случай для многих сортировок вставками; проверяет, нет ли у нас «анти-оптимизаций»;
- `reversedData` — худший случай для наивных сортировок вставками/обменами;
- `fewUniqueData` — дегенерация на дубликатах: ломает наивные реализации и плохо влияет на счётчики поразрядной сортировки.

**Точка контроля (стресс-тест):** теперь, когда есть генератор, — 100 случайных массивов до 500 элементов, значения на всём 64-битном диапазоне (`x = rnd()` без остатка!), сравниваются с `std::sort`. Прогнать и `radixSortBits`, и `mergeSort`:

```cpp
bool ok = true;
for (int t = 0; t < 100 && ok; t++) {
    int n = rnd() % 500;
    vector<uint64_t> a(n);
    for (auto& x : a) x = rnd();   // весь 64-битный диапазон: тестируются все 8 проходов
    vector<uint64_t> b = a;
    sort(b.begin(), b.end());
    radixSortBits(a);
    ok = (a == b);
}
```

## Шаг 2.3 — измеритель

```cpp
using Clock = chrono::steady_clock;

template <typename SortF>
double measure(const vector<uint64_t>& data, SortF sortFn, bool verify) {
    vector<uint64_t> a = data;      // всегда сортируем копию
    auto t0 = Clock::now();
    sortFn(a);
    auto t1 = Clock::now();
    if (verify && !is_sorted(a.begin(), a.end())) {
        cerr << "ERROR: array is not sorted!" << endl;
        exit(1);
    }
    return chrono::duration<double, milli>(t1 - t0).count();
}

template <typename SortF>
double measureMedian(const vector<uint64_t>& data, SortF sortFn, int runs = 5) {
    vector<double> times;
    for (int i = 0; i < runs; i++) times.push_back(measure(data, sortFn, i == 0));
    sort(times.begin(), times.end());
    return times[times.size() / 2];
}
```

## Типичные ошибки
- Замеры без `-O2` → radix «странным образом» выигрывает в разы больше.
- Первый прогон в замере (прогрев кэша) попал в медиану — нужно 5+ прогонов.
- Сравнение времени на разных типах данных между собой (random vs sorted).

# Этап 3. Внешняя сортировка (20 мин)

## Постановка

Отсортировать файл из $N$ чисел, если памяти хватает только на $M \ll N$ чисел. Файлы берём **текстовые, по одному числу в строке** — их можно открыть в редакторе и проверить глазами, а чтение/запись делаются обычными `>>` и `<<`. (Бинарный формат — быстрее и компактнее, но требует побайтового чтения; вынесен в ДЗ.)

Схема — **внешняя сортировка слиянием (external merge sort)**:

1. Читать файл кусками по $M$ чисел; каждый кусок сортировать в памяти (любой сортировкой) и писать во временный файл `chunk_i`.
2. Слить все отсортированные куски в один файл **k-way merge**: держать «текущий элемент» каждого куска в куче (`std::priority_queue`), всегда выписывать минимальный и читать следующий из его куска.

Время: чтение/запись каждого числа $O(\log k)$ раз, где $k$ — число кусков; итог $O\!\left(n \log \frac{n}{M}\right) + O(n)$ I/O.

## Шаг 3.1 — генерация и нарезка на куски

```cpp
const size_t CHUNK = 100000; // чисел в куске: 100 000 чисел uint64 = 0.8 МБ памяти

void generateInput(const string& path, int n) {
    ofstream out(path);
    for (int i = 0; i < n; i++) out << rnd() % 1000000000 << "\n"; // rnd() — генератор из этапа 2
}

vector<string> createSortedChunks(const string& inPath) {
    ifstream in(inPath);
    vector<string> chunkNames;
    vector<uint64_t> buf;
    int chunkId = 0;

    uint64_t x;
    while (in >> x) {
        buf.push_back(x);
        if (buf.size() == CHUNK) {
            sort(buf.begin(), buf.end());
            string name = "chunk_" + to_string(chunkId++) + ".tmp";
            ofstream out(name);
            for (uint64_t v : buf) out << v << "\n";
            chunkNames.push_back(name);
            buf.clear();
        }
    }
    if (!buf.empty()) { // последний неполный кусок!
        sort(buf.begin(), buf.end());
        string name = "chunk_" + to_string(chunkId++) + ".tmp";
        ofstream out(name);
        for (uint64_t v : buf) out << v << "\n";
        chunkNames.push_back(name);
    }
    return chunkNames;
}
```

## Шаг 3.2 — k-way merge через кучу

```cpp
struct HeapItem {
    uint64_t value;
    int fileIdx;
    bool operator>(const HeapItem& o) const { return value > o.value; } // нужен для компаратора в pq, можно добавить на этапе создания кучи
};

void mergeChunks(const vector<string>& chunkNames, const string& outPath) {
    vector<ifstream> inputs;
    int k = chunkNames.size();
    for (int i = 0; i < k; i++) inputs.emplace_back(chunkNames[i]);

    priority_queue<HeapItem, vector<HeapItem>, greater<HeapItem>> heap; // тип элемента, контейнер где хранить, компаратор
    for (int i = 0; i < k; i++) {
        uint64_t v;
        if (inputs[i] >> v) heap.push({v, i});
    }

    ofstream out(outPath);
    while (!heap.empty()) {
        HeapItem it = heap.top();
        heap.pop();
        out << it.value << "\n";
        uint64_t next;
        if (inputs[it.fileIdx] >> next) heap.push({next, it.fileIdx});
    }
}
```

### Как читать `priority_queue` с тремя параметрами

Частая путаница: «priority_queue же принимает один параметр». На самом деле три, но у двух есть значения по умолчанию, поэтому обычно пишут один:

```cpp
template <class T, class Container = vector<T>, class Compare = less<T>>
class priority_queue;

priority_queue<int> h1;                                // max-куча: наверху наибольший
priority_queue<int, vector<int>, greater<int>> h2;     // min-куча: наверху наименьший
```

Разбор строки `priority_queue<HeapItem, vector<HeapItem>, greater<HeapItem>> heap;`:

1. `HeapItem` — тип элемента кучи;
2. `vector<HeapItem>` — контейнер, на котором куча хранит данные (по умолчанию — как раз `vector<T>`, здесь прописан явно);
3. `greater<HeapItem>` — компаратор. Куча кладёт наверх элемент, который «наибольший по компаратору»: с дефолтным `less` это максимум, а с `greater` сравнение «переворачивается» и наверху оказывается **минимум** — для слияния нужен именно он.

Чтобы `greater<HeapItem>` компилировался, в `HeapItem` определён `operator>` — именно его вызывает компаратор. Простая проверка понимания: что окажется наверху у `priority_queue<int, vector<int>, less<int>>` после `push(3), push(7), push(5)`? (7 — потому что `less` даёт max-кучу.)

Здесь пригодится treap с пары «Декартово дерево» — куча здесь та же идея «минимум наверху».

## Шаг 3.3 — проверка результата

Файл большой, поэтому проверяем потоково: (а) каждая следующая позиция $\geq$ предыдущей; (б) количество чисел совпадает с входом. Для строгой проверки перестановки — сравнивать гистограммы или суммы/суммы квадратов.

**Точка контроля:** 1 000 000 чисел при `CHUNK = 100 000` → 10 кусков, выход проверен, временные файлы удалены (`fs::remove`). Генерация + сортировка занимают пару секунд. Кто справился быстрее — запускает 10 000 000 чисел дома.

## Типичные ошибки
- Читать кусок «до конца файла» с буфером фиксированного размера и потерять последний неполный кусок.
- Открывать все `ifstream` в цикле и не хранить их (поток уничтожится и закроет файл).
- Перепутать `>` и `<` в компараторе кучи: `priority_queue` по умолчанию — **max**-куча, для минимума нужен `greater<HeapItem>`.
- Сравнить `buf.size() == CHUNK`, где `CHUNK` имеет другой тип, и ловить странности сравнения знакового/беззнакового — держать типы согласованными (`size_t`).
